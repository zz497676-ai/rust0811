# cube3 — 三维表格 技术规格书

> 一个把「层(Layer)」提升为一等公民的三维电子表格。单元格地址是 `(层, 行, 列)`,
> 公式可以跨层引用、跨层聚合、跨层填充。核心库 + 终端 TUI,纯 Rust 实现,支持与
> `.xlsx` 双向互通。

本目录是**实现规格**,不是实现代码。文档面向执行者(Codex 或人类工程师),
目标是:读完之后**不需要再做任何架构决策**即可动手编码。

## 给执行者的须知

**1. 按里程碑顺序推进,不要跳跃。**
[07-milestones.md](07-milestones.md) 定义了 M0 → M9 的严格顺序,每个里程碑声明了它依赖的
前置里程碑。一个里程碑的验收测试全部通过之前,不要开始下一个。原因很实际:公式引擎的
依赖图(M4)会重构 M3 的求值入口,TUI(M8)会大量调用 M1–M7 的 API —— 顺序颠倒会导致
返工。

**2. 每个里程碑结束时必须跑通:**

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

三条全绿,才算这个里程碑完成。

**3. spec 没写到的地方,按「与 Excel 一致」处理。**
本项目的语义基线是 Excel。凡是 spec 未明确规定的边界行为(空单元格参与运算、类型强转、
错误优先级……),一律向 Excel 对齐,并在实现处写一行注释说明依据。如果 Excel 的行为本身
就不明确,选择最简单的实现,加 `// TODO(spec-gap):` 注释,不要自行发明复杂规则。

**4. spec 里的 Rust 签名是契约,不是草稿。**
[02-data-model.md](02-data-model.md) 给出的公开类型名、字段名、方法签名应当照实实现。
私有实现细节(内部辅助函数、字段排布)自由发挥。如果发现某个签名确实不可行(比如借用
检查过不去),**改它,但要在 PR/提交说明里写清楚改了什么、为什么** —— 因为下游文档
(04/05/06)引用了这些名字。

**5. 第三方 crate 的 API 以其当前文档为准。**
spec 中出现的 `calamine` / `rust_xlsxwriter` / `ratatui` 只描述**意图**(读什么、写什么、
渲染成什么样),不规定具体调用签名。这些 crate 的 API 在版本间会变,请以 `cargo doc --open`
或 docs.rs 上对应版本的文档为准。

**6. 不要引入 spec 未列出的依赖。**
依赖清单见 [07-milestones.md M0](07-milestones.md#m0-项目脚手架)。确实需要新依赖时,
先说明理由。特别地:**公式解析器必须手写**,不要引入 `nom` / `pest` / `chumsky` —— 理由见
[04-engine.md](04-engine.md#为什么手写解析器)。

## 一句话理解这个项目

Excel 里,你要做「12 个月各自一张表、再汇总」这件事,得写 `=SUM(Sheet1:Sheet12!B2)`,
而且这种 3D 引用只在少数函数里能用,层与层之间没有相对关系可言。

cube3 里,层是一根真正的轴:

```
=SUM(*!B2)              → 所有层的 B2 求和
=DELTA(B2)              → 本层 B2 减去上一层 B2(环比),可跨层复制
=SUM(Q1:Q4!B2:B10)      → 4 个层 × 9 行构成的长方体求和
=L[-1]!B2 * 1.05        → 基于上一层同位置做推算
```

再加上一个 Excel 没有的交互:**深度视图** —— 光标停在任意单元格上按 `d`,侧栏纵向列出
这个 `(行, 列)` 位置在**所有层**中的值,一眼看穿它沿深度轴的全部变化。
